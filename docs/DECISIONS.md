# Decisions

One line per decision: what was chosen, why, and the alternative that was not taken.

| # | Decision | Why | Alternative |
|---|----------|-----|-------------|
| 1 | Backend venv uses the 64-bit Python 3.12 (`py -3.12`), not the 32-bit `python` on PATH. | Several wheels (argon2, pydantic-core) and Prowler expect 64-bit; the PATH `python` is 32-bit. | Using PATH `python` and building wheels from source. |
| 2 | Prowler belongs in its own environment (attempted locally as `.vp`), never in the app venv; the app only talks to it as a subprocess. | Prowler pins many libraries; isolating it avoids version fights with FastAPI/Pydantic. | One shared venv. |
| 3 | OSCAL 1.1.3 schemas are vendored from the NIST GitHub release; JSON Schema `pattern` keywords are evaluated with the `regex` package. | The schemas use `\p{L}` Unicode classes, which Python's `re` cannot compile. | Skipping pattern checks, or a Node-based validator. |
| 4 | Priority change (2026-11-17, from the project owner): core first — catalog, evidence engine, scoring/drift/dashboard, one report, demo seed + README — then the assessment workflow; processing register, licensing tracker and breach clock become stretch goals in that order. | Owner instruction mid-build. | Original 8-phase order. |
| 5 | A thin skeleton (auth, roles, audit log, i18n/RTL, app shell) is still built before the catalog. | Every core screen needs login, role checks and i18n from the first string; retrofitting i18n was explicitly ruled out. | Building the catalog with no shell. |
| 6 | Primary users are compliance consultants / DPOs serving several small organizations, plus in-house IT teams. Tenancy stays one organization per install; a consultant runs one install (one `PDPL_DATA_DIR`) per client. **Superseded by #34.** | Keeps the settled single-tenant model and its simple access control while still serving multi-client consultants. | Multi-tenant data model. |
| 7 | The headline number is called a "readiness score", always shown with the split of automated / self-attested / not-assessed requirements, and never labelled "legal compliance". | Automated checks only cover technical safeguards; owner asked not to overstate. | Calling it a compliance score. |
| 8 | Prowler 5.50.0 is **not installed locally**. Windows' 260-character path limit breaks the install (msgraph-sdk and Prowler's own check directories exceed it, even from a 2-letter venv folder); enabling long paths is a system setting and off-limits. Check IDs, the framework format and the OCSF writer were read from the official wheel instead, the framework file was validated with Prowler's own `load_compliance_framework`, and CI installs real Prowler on Linux and re-checks every ID. | Hard limits forbid system changes; CI has no path limit. | Enabling Windows long paths; installing outside the project folder. |
| 9 | Prowler cannot assess Linux hosts (5.50.0 providers: alibabacloud, aws, azure, cloudflare, e2enetworks, gcp, github, googleworkspace, huaweicloud, iac, image, kubernetes, linode, llm, m365, mongodbatlas, nhn, okta, openstack, oraclecloud, scaleway, stackit, vercel), so a stdlib-only, read-only Python 3.6+ collector emits the same OCSF shape. | Python 3 is on virtually every Linux server; emitting JSON from POSIX sh is fragile. | A POSIX shell script. |
| 10 | The Linux mapping uses Prowler's compliance-framework schema too (Provider "Linux"), so one loader reads both mappings. | One format to learn and review. | A bespoke mapping format. |
| 11 | AWS fixtures are synthetic findings generated in Prowler 5.50.0's exact OCSF shape and validated with `py_ocsf_models`; the demo's weekly history is generated by the same code. | No AWS account may be scanned. | Hand-written partial findings. |
| 12 | "Not applicable" is ignored while a mapped check fails (the systems evidently exist); the requirement takes the automated status capped at partial. Stale evidence is flagged but still scored. "Not assessed" counts as 0 in the score. | Prevents hiding a failing technical control behind N/A; keeps the score honest about unanswered requirements. | Letting N/A always win; excluding not-assessed items from the denominator. |
| 13 | A findings file is split into one run per (provider, account/host), and the same file (by SHA-256) cannot be imported twice. | Drift is computed per target; duplicate imports would fake history. | One run per file. |
| 14 | Anything that looks like an AWS key id, secret key, session token, bearer token or private key is redacted from findings before storage. | Cloud credentials must never reach the database, logs or exports. | Trusting Prowler output to be clean. |
| 15 | PDF fonts: IBM Plex Sans Arabic subsets from the npm package `@fontsource/ibm-plex-sans-arabic`, merged with fontTools into one TTF per weight and renamed "PDPL Sans" (committed, OFL). Arabic is shaped with `arabic_reshaper` and reordered per line with `python-bidi`. | ReportLab needs TrueType and has no OpenType shaping; the npm subset maps the Arabic presentation-form codepoints the reshaper emits. Packages only, no system fonts. | WeasyPrint/HarfBuzz (system installs), Windows system fonts (not portable), English-only PDFs. |
| 16 | OSCAL assessment-results import restores automated check results (observations with method TEST) through the normal ingestion pipeline; it does not overwrite self-attested answers. | Lets a consultant move evidence between installs without silently replacing a DPO's answers. | Importing answers too. |
| 17 | Licence: MIT, copyright lumidren. Bundled NIST schemas, fonts (OFL) and Prowler metadata (Apache-2.0) keep their licences. | Permissive and compatible with contributing the framework file to Prowler (Apache-2.0). | Apache-2.0 for the whole repo. |
| 18 | Dashboard cards for deadlines and breach clocks only appear once those features exist (`features` flags from the API). | An empty "no deadlines" card for a feature that does not exist yet would mislead. | Always-visible empty cards. |
| 19 | Breach clocks count from the moment the organisation became aware (`discovered_at`), with configurable hours (`PDPL_BREACH_REGULATOR_HOURS` = 72, `PDPL_BREACH_INDIVIDUALS_HOURS` = 144 as a clearly marked placeholder). The UI escalates under 24 h (warning) and 12 h (urgent). | The brief gives 72 h from awareness for the regulator but no figure for individuals; a visible placeholder beats an invented deadline. | Counting from the occurrence time; hard-coding a second deadline. |
| 20 | A date-time entered without an offset is read as Cairo local time; tracker dates are stored at 12:00 UTC so their calendar day is the same in UTC and Cairo. | Users think in Cairo time; storing midday avoids a date sliding to the previous or next day across the UTC+2/+3 offset. | Storing local times; storing dates at midnight UTC. |
| 21 | Renewal and review reminders are in-app only (obligations page and dashboard), generated by the in-process scheduler. | There is no mail server to configure and nothing may be sent on the user's behalf without setup; in-app reminders work everywhere. | Email or SMS reminders. |
| 22 | Notification templates fill only the facts recorded on the incident; anything missing is marked "[to be completed: …]" and counted. | A pre-filled notice must never invent facts about a breach. | Generic placeholder prose. |
| 23 | Register exports: CSV with bilingual headers for the controller and processor layouts, PDF per language. No XLSX. | CSV opens in Excel without another dependency; the layouts are modelled on the templates described in the brief and labelled as unverified. | Adding openpyxl for XLSX. |
| 24 | The licensing questionnaire maps one yes/no question to each licence or permit and never says "required"; the applicability screener encodes the brief's CBE rule (supervised entities out of scope except money transfer and currency exchange). | The brief asks for "likely required" wording and a screener; the rules are kept small and visible so a lawyer can correct them. | A weighted scoring questionnaire. |
| 25 | The evidence pack is a ZIP with every evidence file and check run, `manifest.json`/`manifest.csv`, and `sha256sums.txt` verifiable with `sha256sum -c`. | Anyone can verify integrity without Sijill. | A PDF-only pack. |
| 26 | Global CSS: grid children may shrink (`min-width: 0`) and horizontal scroll containers are positioning contexts. | Found in the accessibility pass: wide tables pushed pages past phone width, and screen-reader-only header labels widened the page in RTL. | Fixing each page separately. |
| 27 | The settings API reports only whether an AWS profile or role is configured, never the values. | Credentials and their references stay out of the browser and the audit log. | Showing the profile name. |
| 28 | Governance extension (2026-11-17, owner asked to raise the product from a 7.5 to a 9 as a GRC tool): remediation tasks, risk register, requests from individuals, vendor/processor register, DPIAs, policy library and TOTP two-step sign-in, all wired into the dashboard, drill-down, PDF report and OSCAL POA&M. | Closes the gaps named in the review: no remediation workflow, no risk register, no DPIA/request/vendor/policy modules, password-only sign-in. | Leaving them to other tools. |
| 29 | The six modules share one generic CRUD router (`_crud` in `routers/governance.py`) with per-module validation and audit actions; approvals and risk acceptance are separate endpoints. | Same list/get/create/update shape everywhere, and approvals cannot be smuggled in through an ordinary update. | Six hand-written routers. |
| 30 | Risk acceptance, DPIA approval and policy approval are Admin-only (`risks.accept`, `approve`); a risk acceptance needs a written reason and expires within `PDPL_RISK_ACCEPTANCE_MAX_DAYS` (365). Editing an accepted risk or an approved DPIA clears the decision; editing a policy's wording under the same version keeps its approval, a new version needs approval again. | Separation of duties: the DPO prepares, management signs off, and sign-offs do not live forever. | Letting the DPO approve their own work. |
| 31 | Risk scores are likelihood × impact on 1–5 scales with bands 1–4 low, 5–9 medium, 10–16 high, 20–25 critical; DPIA screening shows "likely needed" at two or more of eight criteria. Both are labelled as practice conventions, not law, and listed in LEGAL-REVIEW. | Widely used conventions a reviewer can recognise and change. | Inventing PDPL-specific thresholds. |
| 32 | Requests from individuals are due `PDPL_DSR_RESPONSE_DAYS` (30) after receipt, shown on the page and in Settings as an unverified placeholder. Requester fields ask for a reference, not more personal data. | The response period in the law is unverified; a visible setting beats a hard-coded guess, and the tracker itself should minimise personal data. | No clock at all. |
| 33 | TOTP secrets are stored in the database column in clear, like the password hashes beside them; codes are checked ±1 step with the last used step stored to block replay, and failures share the login throttle. | Encrypting them with a key stored on the same server adds little; the database and `secret.key` share one trust boundary. | Encrypting with a key derived from `secret.key`. |
| 34 | Several organisations per install (2026-11-18, raising the product further for its primary users). Every organisation-owned table carries `org_id`; a SQLAlchemy `do_orm_execute` hook adds `org_id = <current>` to every ORM select, update and delete, and a `before_flush` hook stamps new rows. A session that names no organisation works on organisation 1, never on all of them. The current organisation comes from a `pdpl_org` cookie that `current_user` checks against the account's access on every request (falls back to one the user may open; 403 if none). Users and install-wide audit events (accounts, organisations) are shared; every other audit entry records its organisation, which is part of its hash. | Consultants were told to run one install per client, which hides the portfolio view they need most. Filtering in one place means a new endpoint cannot forget it; tests check every module by list and by id. | One database per client (users and foreign keys would have to be copied between files); `org_id` filters written into each query by hand. |
| 35 | Day counts ("2 days overdue", "due today") use today's date in `PDPL_TIMEZONE_DISPLAY` (Africa/Cairo), not in UTC. Amends #20: stored dates stay at 12:00 UTC. | Found when the suite ran after midnight Cairo time: from 00:00 to 02:00 a deadline due today read as due tomorrow. | Keeping UTC days. |
| 36 | Scheduled collection (Prowler subprocess, inbox folder) feeds one organisation, `PDPL_COLLECT_ORG_ID` (default 1); "Run collection now" is refused elsewhere and the page says why. Other organisations import findings files (UI or `import-findings --org`). | Cloud credentials come from the server's environment, so they belong to one client; per-organisation credentials would mean storing secrets in the database. | Storing AWS profiles per organisation. |
| 37 | The UI creates new non-admin accounts with access to the organisation open now; "all organisations" is a deliberate choice. The API default stays "all" so single-organisation installs and scripts behave as before. Admins always see every organisation. | A client's own staff or auditor should not see the consultant's other clients by accident. | Defaulting to all organisations in the UI. |
| 38 | A real-account lab (`scripts/aws-lab`) is provided but not run: the hard limits forbid scanning a real AWS account from this machine. It confirms the account interactively, never handles credentials, keeps the bucket's public-access block on and attaches the open security group to nothing. A test keeps the checks its README promises in step with the mapping. | Lets the owner turn "synthetic" into "demonstrated" in about fifteen minutes on an account they control. | Leaving real-account proof undocumented. |
| 39 | Renamed PDPL-Ready to **Sijill** (سجل, "register") on 2026-11-18, at the owner's request. The display name, reports, OSCAL namespace (`urn:sijill:oscal`), Linux collector id (`sijill-linux`), TOTP issuer and lab names changed; catalogs and exports using `urn:pdpl-ready:oscal` and findings from the old collector id still load. Identifiers that name the law stay: the `PDPL_` environment variables, the `pdpl_session`/`pdpl_org` cookies, the `X-PDPL-Request` header and file names such as `pdpl-catalog.json` and `pdpl_linux_collector.py`. In Arabic sentences the product is "منصة سجل", since "سجل" alone reads as the common noun. The repository folder keeps its name because the virtualenv records absolute paths. | A name that is not tied to one law and reads naturally in both languages; changing settings and cookie names would break existing installs for no user benefit. | Renaming every identifier; keeping PDPL-Ready. |
